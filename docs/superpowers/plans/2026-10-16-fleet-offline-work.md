# B — Durable Offline Fleet Work Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let provisioned authorized field users create ticketed runs and record all work/evidence through outages, restarts and intermittent reconnection, with lossless scoped recovery and no duplicate canonical tickets or charges.

**Architecture:** Evolve the existing offline Fleet sequence into one durable fact journal plus dependency-aware outbox. Native uses the existing SQLCipher/FileSystem foundations; provisioned web uses IndexedDB/Web Crypto and a cached offline shell. Connected v2 actions use the same journal/command intake. Server authority remains current and canonical, and unresolved performed work remains visible rather than being discarded or silently rebound.

**Tech Stack:** Existing TypeScript/Zod/Expo SQLite SQLCipher/SecureStore/FileSystem, browser IndexedDB/Web Crypto, Express/PostgreSQL and current evidence/private storage; no new external library/provider.

**Spec:** [Operating scope](../../fleet-operations-scope-ok-tx-2026-10-16.md), especially section 10 and RF1/RF5 in the [master plan](2026-10-16-fleet-commercial-operations.md).

## Global Constraints

All master constraints apply. A local reference is never a canonical ticket number. Offline authority is bounded by the last verified account/company provisioning, not supplied by the model or a client-supplied role. Local capture remains possible when a reference/price/compliance check is unresolved; reconciliation never invents commercial authorization. Conflicts isolate canonical application, not new fact capture. Sign-out locks pending original-scope work instead of deleting or showing it to another account. No record is labeled synced/submitted/uploaded before its actual acknowledgement.

## Review Focus

October 16 scope clarification: journal saved Run-definition references separately from each ticket-bound activity. A Run is an Origin/Destination transport order; dispatch matches a reusable Detail to that order. Repeating it on one ticket creates distinct activities, not duplicate order definitions. Driver pool and assigned activity access require current company/Detail authority, not a driver-to-site assignment; customer/billing authority remains explicit at canonical reconciliation.

- Server commits before response loss: look up the operation receipt and return exactly the same canonical result.
- One run conflicts with a changed assignment/closed ticket: other runs sync and this run continues collecting facts.
- OS kills the app after journal/photo writes: original records and bytes survive without dangling success labels.
- User signs out/changes company with pending work: no deletion, cross-account exposure or replay under a revoked token.
- Historical observation time differs from server receipt time: preserve both without silently altering existing billing/timing rules.

**Interfaces:** `FleetWorkScope` is verified `{userId,companyId,deviceId,provisioningId}`. `FleetLocalReference` is discriminated `local:{id,kind}` versus `canonical:{id,kind,version}`; kinds include ticket/run/Detail/location/evidence. Local IDs are UUIDs; canonical ticket IDs stay positive integers and canonical run/Detail/location/evidence IDs stay UUIDs, as required by A1. `FleetWorkCommand` is a strict versioned discriminated union with `operationId`, scope, original capture time/time zone, dependencies, base revisions and typed payload. Variants cover create ticket/run, bind existing ticket, acknowledge, inspect, start/pause/resume, pickup/delivery/cycle evidence, damage/notes, close and office reconciliation/finalization intents. Import actual A `FleetDetailSnapshot`/route, C policy/assessment and D `FleetPricingIntent`/quantity schemas; no `unknown` action payload or duplicate snapshots. Unplanned work/provisional locations are explicitly unresolved, not fake server identities.

`FleetWorkReceipt` is `applied | duplicate | needs_reconciliation | retry_later | denied`, with operation fingerprint, canonical mappings/revisions, reason and safe readback references; no `synced` on denial. `FleetReconciliationCase` defines reason (`closed_ticket | changed_assignment | resource_conflict | missing_authority | unresolved_location | unresolved_price | expired_session | invalid_dependency`), original references and allowable authorized resolutions. `FleetWorkJournal` port exposes `append(command): Promise<LocalSaveReceipt>`, `appendFact(fact): Promise<LocalSaveReceipt>`, `listPending(scope,cursor)`, `readMappings(scope,ids)`, `applyReceipt(scope,receipt)`, `readStatus(scope)`, `lockScope(scope)` and separate evidence/reference-cache ports. `nextFleetWorkBatch(state,now): FleetWorkCommand[]` schedules dependency-ready commands with per-run order, independently across runs. Immutable facts stay separate from mutable delivery status.

## Acceptance handoff

B is ready when durable native/browser capture, ticket-choice references, ordered replay, exactly-once canonical effects, independent evidence receipts, private account recovery and office conflict resolution pass fault tests. Provisioning/sign-in still needs initial connectivity, and another offline driver's device cannot receive new remote assignments. M1–M4 complete the user experience, notifications, physical-device acceptance and full release; until then this is an implementation milestone, not a shipped offline guarantee.

# D — Fleet Commercial Pricing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Price each run/cycle from its actual authorized agreement, preserve precise quantities/sub-cent rates, itemize additional charges and reconcile every financial consumer before explicit office ticket submission.

**Architecture:** Add exact decimal helpers and versioned rate/charge snapshots to existing catalog, approvals, runs, tickets and line records. One effective financial-line adapter serves new and legacy readers. Keep mandatory new/shared tickets, current partner-owned approvals and historical billing semantics.

**Tech Stack:** Existing TypeScript/Zod/PostgreSQL/Orval; dependency-free BigInt decimal arithmetic, no paid rate/tax provider.

**Spec:** [Commercial scope](../../fleet-operations-scope-ok-tx-2026-10-16.md), sections 1, 12, 15 and 16; [master plan](2026-10-16-fleet-commercial-operations.md).

## Global Constraints

All master constraints apply. No invented production price, silent zero for unpriced work, implicit partner approval or retired catalog publish route. Drivers report operational quantities without gaining price/finance permissions. Every run has a ticket choice; office reviews runs and explicitly finalizes shared tickets. Exact charge authority survives catalog changes. New precise values must never be silently forced into legacy two/four-decimal fields or hidden in unexplained lump sums.

## Review Focus

October 16 scope clarification: price/review each execution of a saved Run transport order. One Detail may execute the same Origin/Destination order repeatedly on an eligible shared ticket, then another order on another ticket. The saved Run definition is independent of ticket identity and the company driver pool; no driver-to-site assignment is required. Preserve canonical activity IDs and immutable per-activity billing snapshots.

- A second shared-ticket run has a different approved rate: do not inherit the first ticket's single rate.
- A small decimal rate times a large quantity differs between ticket, invoice and report because a reader truncates at four decimals.
- Detention overlaps hourly service, or a ticket minimum is charged once for every run.
- Offline replay/returned review repeats a charge or a driver edits an office-approved price.
- Vendor live catalog changes after partner approval: the immutable approved authority remains the source.

## D1: Exact arithmetic, precision storage and strict pricing contracts

**Files:** create `lib/db/src/format/exact-decimal.ts`, API test `artifacts/api-server/src/lib/exact-decimal.test.ts`, `lib/api-zod/src/fleet-pricing.ts` and `fleet-pricing.test.ts`; modify relevant package exports and `lib/api-zod/src/index.ts`; extend existing `lib/db/src/schema/{vendorWorkTypes.ts,partnerVendorWorkTypeApprovals.ts,siteWorkAssignments.ts,ticketLineItems.ts,invoiceLines.ts}`; create `lib/db/src/scripts/apply-fleet-pricing.ts`, `migrate:fleet-pricing` package entry and migration tests. Use the existing API test runner for the helper; `@workspace/db` currently has no Vitest test script/dependency.

**Interfaces:** exact helpers `parseExactDecimal(value:string): ExactDecimal`, `addExact(a,b): ExactDecimal`, `subtractExact(a,b): ExactDecimal`, `multiplyExact(a,b): ExactDecimal`, `divideExact(a,b,{scale,rounding}): ExactDecimal`, `roundExact(value,{scale,rounding}): ExactDecimal`, `formatExact(value): string`. Accept input values fitting signed `numeric(24,9)`, reject more than nine fractional digits or out-of-range magnitude before persistence, and retain full intermediate precision until explicit rounding. No `Number` monetary math. Zero division rejects. USD charge rounding is two decimals, half-away-from-zero, applied once to each charge; totals sum rounded charges. Other currencies require explicit supported scale, not a guessed USD default.

`FleetRateCardRevision` stores immutable service/approval reference, basis, currency, decimal rates, effective interval, allowance/minimum/rounding rules and approver. Bases: existing `per_job | per_hour | per_day | lump_sum` plus `per_load | per_mile | per_barrel | per_us_gallon | per_short_ton`. UI may label `per_job` “per run” without rewriting old units. `FleetPricingIntent` is an explicit `priced` snapshot request or `unpriced` reason/reference; no missing-value-to-zero adapter. `FleetCharge` contains stable identity/revision, run/cycle/ticket/service references, charge kind, precise quantity/unit/rate/amount, rounded currency amount, tax treatment, evidence/approval and eligible surcharge/adjustment references. `FleetQuantityEvidence` distinguishes planned/picked-up/delivered/accepted/billable values, unit and recorded source. `FleetTicketBillingV2` records compatibility scope and reviewed charge references; all exported schemas are strict.

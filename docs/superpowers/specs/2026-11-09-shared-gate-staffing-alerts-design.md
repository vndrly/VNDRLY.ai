# Shared Gate staffing alerts

## Confirmed behavior and purpose

Staffing will be brought online gradually. MidCon Solutions vendor1054 notifications remain indefinitely held until John explicitly instructs resume; implementing these features never lifts that hold. In normal operation one staffing gap is one shared incident. The first currently authorized company admin explicitly acknowledges it using push, SMS tied to that alert, web, or iOS; this stops reminders/escalations for all recipients. Login, delivery, read state and assigning a worker are not acknowledgment or proof of actual coverage.

The navigation notification bell opens a red escalated workflow-breaker card explaining the gate, shift and shortage, with acknowledgment confirmation and a direct calendar action. Watch Radar links to the same exact company/site/station/shift/date. A critical unacknowledged alert blinks red; after acknowledgment it remains red with the admin name/time until coverage is restored, with no blinking/reminder noise. Future unassigned watches are warnings, not proof of an empty current booth. Include text status and respect reduced motion.

Calendar permits eligible assignment/reassignment and the established Assume Watch action. A saved watch restores actual coverage; assignment alone does not. An eligible admin/office employee may cover personally using normal Gate watch/ticket rules. Gate Mode is a view, not a permanent role or custody change: returning to Admin/Work Hub is always allowed while the watch remains active. Only an explicit end watch/handoff changes custody; closing pages, logging out or losing connectivity must not silently end it.

## Approach and implementation choices

Use one additive persisted staffing-incident table, with stable ID/SMS code and episode lifetime, plus a notification mapping table. Per-recipient acknowledgment cannot implement the user's shared stop. Do not use transient browser state or mark-all-read to represent responsibility. Reuse existing notification channels, signed sessions, recipient authorization and automatic watch/ticket transaction. Add no provider, dependency, global role mutation or destructive migration.

An incident is scoped to shift, gate/site and owning organization. Serializing by shift prevents duplicate active episodes. First admin acknowledgment wins atomically and is idempotent; other users see the same winner. Stop queued retries and recheck before delivery; never claim already-started provider requests can be recalled. Keep coverage and incident state distinct. A new gap after real restoration can create a new incident; routine worker evaluations, severity changes and repeated 10-minute reminders cannot reset acknowledgment.

During a company hold keep staffing facts available but suppress alarm flyouts, pulses, notification creation and outbound delivery. Do not release old startup reminders automatically. Preserve history and opt-in evidence.

SMS acknowledgments require a signed Twilio inbound request, exact alert code, and a currently eligible admin matching the SMS-consented sender number. Ambiguous, revoked, unrelated, malformed or opt-out messages do not acknowledge. Handler/configuration readiness is separate from verified physical SMS delivery; send no live customer tests. Password/access flows remain separate from operational alerts.

## Interfaces

Shared type: `GateStaffingAlert` in `@workspace/gate-booth`, exported from `staffing-alerts.ts`.

- `GET /api/gate-staffing-alerts` -> `{alerts: GateStaffingAlert[], notificationsPaused:boolean}` current company/site scope; held users receive facts with paused flag, never alarm UI.
- `POST /api/gate-staffing-alerts/:id/acknowledge` body `{channel?:'web'|'ios'|'push'}` -> `{alert:GateStaffingAlert}`. Current company admin only, first writer retained.
- Existing owned `POST /api/notifications/:id/acknowledge` routes mapped staffing notices to the same shared operation; legacy notifications retain existing semantics.
- Provider inbound `POST /api/twilio/staffing-alert-reply` authenticates signature, SMS code and current admin, invokes same shared acknowledgment with channel sms, returns empty TwiML without unsolicited response messages.
- Calendar href generated by server retains `siteId`, `stationId`, `shiftId`, `date` in the shift timezone. UI consumes the returned href directly.

Backend service exports `listGateStaffingAlerts(session)`, `acknowledgeGateStaffingAlert(session,id,channel)`, `staffingAlertForNotification(notificationId,userId?)`, `staffingNotificationMayDeliver(notificationId)`, `cancelStaffingAlertDeliveries(client,alertId)`, `reconcileGateStaffingAlert(notice)`, `resolveCoveredGateStaffingAlerts(stationId)` and shared DTO. Root owns existing notification-delivery integration and SMS router; server agent owns new service/schema/migration/monitor/hook/routes.

## Validation

Use isolated real PostgreSQL for duplicate monitor evaluations, two simultaneous admins, cross-company/stale authority, cancellation/retry races, new episode after restoration, MidCon hold and saved-watch resolution. UI tests cover red warning/acknowledged/resolved/paused states, exact calendar links, account switches, failure/retry and reduced-motion styling. Existing two-gate workflow and automatic ticket remain unchanged. No synthetic live notifications or staffing records.
